# Users Profile Service

Микросервис управления профилями пользователей: создание/изменение/удаление пользователей, блокировки/разблокировки, кэширование и история изменений.
Уведомление другие сервисов системы об изменениях пользовтеля и его статусов

### Архитектура

- **HTTP API**: REST-эндпоинты (`/internal/api/rest/handlers`) для CRUD по пользователям и верификации email.
- **gRPC API**: сервис `UserProfileService` (`api/generation/users/v1/service`) для межсервисного взаимодействия.
- **База данных**: PostgreSQL, слой репозиториев в `internal/repository`, доменные модели в `internal/models`.
- **Кэш и идемпотентность**: Redis (`internal/repository/redis`, `RedisProvider`) для кэша пользователей и хранения идемпотентных ключей.
- **Kafka**:
    - продюсеры (создание, удаление, разблокировка пользователя) в `internal/external/kafka/producer`;
    - консьюмер блокировок `BlockUser` в `internal/api/kafka/consumer/BlockUser`.
- **Внешний gRPC-клиент**: kitchen-сервис в `internal/external/rpc/kitchen/v1/service`.

---

## База данных и миграции

SQL‑миграции лежат в `internal/migrations/sql`:

- `001...007` — создание схемы, таблиц пользователей, таблиц блокировок и заполнение справочника типов блокировки.

**Нюанс:** автоматического раннера миграций нет — миграции нужно прогонять вручную (через `psql`, `migrate`, `goose` и т.п.) до старта сервиса.

---

## Типы блокировок

Справочник типов блокировок (`block_type_dictionary`) и стартовые данные находятся в миграциях:

- **таблица**: описывает типы блокировок (например, временная, перманентная).
- **таблица статусов пользователей**: текущий статус блокировки пользователя, история хранится отдельно (таблица `users_h`).

При изменении/добавлении типов блокировок — обновлять соответствующие SQL‑миграции и бизнес‑логику в `internal/user/block` и `internal/user/unblock`.
